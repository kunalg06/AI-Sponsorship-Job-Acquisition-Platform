- (direction) User deleted the Turso account and removed the Streamlit Cloud deployment on 2026-08-24, then asked to spec the code removal. turso.env deleted the same day.
- (note) Dead surface measured live: src/dbcompat/ 217 lines, tests/test_dbcompat.py 182 lines, libsql dep, app.py:30-75 st.secrets bridge, requirements.txt, packages.txt, .devcontainer/devcontainer.json 33 lines, .gitignore lines 8/18/23-26.
- (decision) dbcompat is deleted outright, not slimmed. All three of its classes (Row, _CursorAdapter, _ConnectionAdapter) exist only to make libsql's bare-tuple rows imitate sqlite3.Row; with libsql gone nothing remains but a two-line fallback. The four db.py modules go back to sqlite3.connect + row_factory. ~400 lines removed for ~8 added.
- (constraint) src/jobs/pdf_export.py and LibreOffice support are OUT of scope and must not be touched. packages.txt is only the Cloud apt manifest; pdf_export finds soffice on PATH or the Windows install path, so PDF export stays a working local feature after packages.txt is deleted.
- (constraint) The libsql duplicate-detection accommodations must go with it: jobs/cli.py:315-317 and jobs/db.py:173-174 both catch a bare ValueError because libsql has no IntegrityError subclass. On plain sqlite3 that branch is unreachable, and leaving it makes a real unrelated ValueError look like a duplicate.
- (constraint) No data migration. data/*.db are already plain SQLite files serving the app today; row counts must be unchanged after the change (jobs 117, sponsors 142649, profile 1, roadmap 1/18) and no file is rewritten.
- (decision) register/db.py's INSERT_BATCH_ROWS=2000 and BUSY_TIMEOUT_MS=15000 stay. Both were Turso/Cloud-motivated but are harmless locally, and reverting them is a separate performance change with its own risk. Their comments must be corrected so they stop citing a Turso round trip and a deploy target that no longer exist.
- (question) .python-version is pinned to 3.13 solely because libsql had no Windows wheel above cp313 (stated in pyproject.toml). Removing libsql frees the pin - unpin now, or leave it as a separate decision?
- (capability) CAP-1 four db modules open sqlite3 directly, dbcompat and its test deleted. CAP-2 duplicate detection catches only sqlite3.IntegrityError. CAP-3 app.py reads env alone, no st.secrets. CAP-4 Cloud packaging artifacts and the libsql dep removed. CAP-5 comments, gitignore and the ledger stop describing dead infrastructure.
