- (direction) User asked for an in-app way to clear the discovery backlog after finding no trigger on the Automate page; approved spec-first per this repo's convention.
- (note) Verified live 2026-08-24: unreviewed Indeed queue is 92 rows. Partition at threshold 85 = keep 13 / discard 78 / unscored 1; at 70 = keep 22 / discard 69 / unscored 1.
- (constraint) list_discovery_queue defaults limit=20 and views/automate.py passes no limit, so the page renders 20 of 92; triage-discovery's --limit also defaults 20. A button wired to those defaults would discard 7 of 78 below-threshold rows and look finished - the silent-partial-action failure family this codebase just spent a commit fixing.
- (decision) The triage control operates on the entire unreviewed queue, not the 20-row display window, and states the count it acted on. Ranking/display stays capped; the action does not.
- (constraint) Dry-run-then-apply must survive into the UI: _cmd_triage_discovery is dry-run by default because it is the one batch mutation no human eyeballs row-by-row, and data/*.db has no backup. A single-click apply would drop that safety.
- (constraint) Unscored rows (match_score NULL) are never discarded - a NULL is absence of information, not a low score (partition_discovery_queue's stated purpose). They stay in the queue for the human.
- (constraint) Discard means mark_discarded setting applied_status='discarded' (recoverable, visible under Jobs List's Discarded filter), never a DELETE - a wrong threshold must cost a WHERE clause, not data.
- (question) Threshold for the UI control: DISCOVERY_TRIAGE_THRESHOLD is 85 but the project's strong_match threshold is 70 and neither is validated against real outcomes. Fixed at 85, or user-adjustable in the UI?
- (capability) CAP-1 preview whole-queue split at a threshold, no mutation. CAP-2 commit the previewed discard as a second distinct action. CAP-3 unscored rows reported and left in queue. CAP-4 result states the queue size acted on, distinct from the 20 displayed.
- (event) Self-validate pass 1 (coherence, Spec Law 1-6 + 8): PASS. Four capabilities each carry intent + success; all five constraints rule something out; four non-goals; success signal is countable (92 -> 14, discarded rows recoverable).
- (event) Self-validate pass 2 (preservation): PASS. Every load-bearing source claim landed - queue depth 92, absent in-app bulk path, cli.py:1114, page read-only over list_discovery_queue, partition_discovery_queue's three buckets, never-hard-filter decision, limit=20 partial-action trap, dry-run rationale, mark_discarded-not-DELETE, tailoring deliberately not invoked, unbacked-up data/*.db. No wrapper-only drops.
- (event) Spec finalized 2026-08-24; one open question outstanding (threshold fixed at 85 vs user-adjustable).
- (decision) Open question resolved: threshold is a UI slider (50-95, step 5) defaulting to DISCOVERY_TRIAGE_THRESHOLD=85, not a fixed constant - neither 85 nor 70 is validated against real outcomes, so the human picks per-run and the help text says so.
